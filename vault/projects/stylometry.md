## Body

Inspiration Traditional SAST scanners detect vulnerabilities in code. They don't detect who wrote it. A developer with stolen credentials can push anything — malware, backdoors, supply chain implants — and the scanner will clear it, because the threat isn't in the code's structure. It's in the identity gap. We were inspired by forensic linguistics: the idea that every author leaves a behavioral fingerprint. Commit hour distributions, token-type ratios, lexical density, base64 entropy clusters, naming convention vectors — each developer has a statistical signature. We built a gate that reads it. What it does STYLOMETRY is a forensic identity gate for GitLab CI/CD pipelines. Every time a Merge Request is opened, it runs seven independent forensic cores against the commit and computes a Multi-Criteria Profile (MCP) score using pure rational arithmetic (fractions.Fraction — zero floating-point drift, SHA-256 deterministic results). The seven cores are: behavioral analysis (temporal and volume anomalies), Shannon/Gini entropy detection (base64 payload injection), semiotic analysis (social engineering patterns in English and Rioplatense Spanish), NLP register drift (lexical density, TTR), chronobiological profiling (circadian commit grids), commit atomicity (topological dispersion), and syntax fingerprinting (AST-level coding style). When two or more cores fire simultaneously, a synergy multiplier escalates the risk — because attackers combining social engineering with obfuscated payloads are more dangerous than the sum of their parts. Verdicts: PASS · WARN · REQUIRE_REVIEW · BLOCK. On BLOCK, the pipeline fails with exit 1 and the Gemini ADK agent closes the Merge Request via GitLab MCP. How we built it The forensic API is a Python 3.12 service deployed on Google Cloud Run. All scoring is deterministic — every metric stored as str(Fraction(...)) in SQLite, never as a float. The autonomous agent layer uses the Google Agent Development Kit (ADK) with Gemini 2.0 Flash and connects to GitLab via MCP (Model Context Protocol) to read pipeline events, post forensic reports to MR threads, close compromised requests, and flag commits for audit — all in one autonomous loop. Author baselines are hydrated from real git history using hydrate_profiles.py, which computes rational behavioral baselines from up to 50 historical commits. Challenges The hardest architectural decision was separating the deterministic forensic layer from the agentic layer. The LLM reads attacker-controlled commit content while holding a privileged GitLab token — that's a real attack surface. We enforced a strict invariant: all blocking decisions are made by the deterministic MCP score, never by the LLM. The agent can reason and explain; only the math can block. The second challenge was false positive rate. Short commit messages have statistically degenerate TTR values regardless of the author. We implemented a MIN_TTR_TOKENS = 10 guard so behavioral stylometry only fires when there's enough text to be meaningful. Accomplishments we're proud of A live demo that ACTUALLY blocks a real supply chain attack: a commit combining CARNEGIE_HELPER_TRAP + URGENCY_INJECTION social engineering + BASE64_PAYLOAD_INJECTION reaches MCP = 1.0 and fails a real GitLab pipeline. The forensic evidence is posted directly to the MR thread by the agent. Also: 11/11 deterministic tests, including one that verifies SHA-256 hash stability across 3 consecutive full pipeline runs. What we learned Identity in software development isn't a binary credential check — it's a probability distribution. A developer's behavioral signature is surprisingly stable and surprisingly hard to fake. An attacker who steals your credentials still has to write like you. What's next Multi-VCS support (GitHub, Bitbucket). Enterprise IAM integration. A global anomaly dashboard visualizing supply chain risk across an organization's full commit history. And extending the semiotic core to cover more languages and cultural social engineering patterns. In-Depth Forensic Analysis The MCP (Malicious Committer Probability) score of 1.0 is broken down as follows: Behavioral Penalty (0.35): The attacker is trying to operate outside normal patterns to avoid scrutiny. TEMPORAL_ANOMALY (3am): Committing code in the middle of the night is a common tactic. It deviates from the author's normal behavior and is timed to occur when security teams and peer reviewers are likely offline. VOLUME/SIZE_ANOMALY (18 files, 4000 lines): A "quick hotfix" should be a small, targeted change. A massive change affecting many files is completely inconsistent with the stated intent. This is a major red flag, suggesting the commit's description is a lie. Semiotic Penalty (0.25): This is the social engineering layer. The commit message is crafted to manipulate and deceive human reviewers. URGENCY_INJECTION ("urgent"): This word is used to pressure reviewers into approving the merge request quickly and without a thorough inspection. It exploits the desire to keep production systems running smoothly. CARNEGIE_HELPER_TRAP ("let me help you"): The attacker frames the malicious act as a helpful gesture. This psychological trick lowers the reviewer's guard by appealing to a sense of teamwork and reciprocity. SYN-001 Synergy: This indicates a known attack pattern where urgency and the "helper trap" are combined for maximum manipulative effect. Entropy Penalty (0.40): This is the technical layer—the smoking gun. BASE64_PAYLOAD_INJECTION: The core of the attack. The attacker knows that raw malicious code (e.g., a reverse shell script) would be easily spotted. By encoding it in Base64, it appears as a harmless, jumbled block of text to both the human eye and basic keyword-based scanners. Execution via exec(base64.b64decode(payload)): This is the trigger. The b64decode() function de-obfuscates the payload, and exec() executes it. This allows the attacker to run arbitrary code that was hidden in plain sight. Why This Combination is so Dangerous in CI/CD The combination of a social engineering pretext and an obfuscated payload is especially potent in a CI/CD context for two main reasons: It Targets Both Human and Machine Defenses: The social engineering in the commit message is aimed at the human reviewer, trying to rush their approval. The Base64 obfuscation is aimed at the machine, designed to bypass automated Static Analysis Security Testing (SAST) tools that aren't configured to detect and decode such payloads. It Abuses the Speed and Privilege of the Pipeline: CI/CD pipelines are built for speed and operate in a privileged environment with access to secrets and production infrastructure. If this commit were approved, the exec() command would run on the build runner. From there, the attacker's malicious payload could: Steal Secrets: Exfiltrate API keys, cloud credentials, and other secrets stored in the CI/CD environment. Poison the Artifact: Inject a backdoor directly into the final container image or software binary, which then gets shipped to production, compromising the application and all its users. Establish a Beachhead: Create a persistent foothold inside your infrastructure, allowing for further attacks. In summary, this attack pattern turns your own trusted, automated infrastructure into the weapon. It leverages a plausible social pretext to trick a person into approving a change that a machine can't easily recognize as dangerous, leading to a high-speed, automated compromise.
