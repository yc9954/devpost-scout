chinwag logo alibaba cloud setup chinwag -qwen intergration frontend and backend instance chinwag playground chinwag studio chinwag editing timeline Chinwag: An AI Showrunner Workspace for Research-Backed Media Production Chinwag is a source-grounded AI production system built on Qwen and Alibaba Cloud. It coordinates research and production agents to move a project from evidence to a rendered, publishable output while preserving the sources, prompts, assets, and edit decisions behind it. Most AI media workflows optimize for the first generation. Chinwag is engineered for everything that must happen next. Generated media is normalized, stored, registered as project state, verified before another agent can depend on it, assembled into a structured timeline, and rendered back into the same workspace. A model response is not treated as finished work; it must become a durable production asset. Production architecture Reasoning and orchestration: qwen3.7-plus across two bounded Qwen Agent teams Media generation: qwen-image-2.0-pro and wan2.7-t2v through DashScope Durable state: PostgreSQL project metadata with OSS-backed sources and outputs Runtime: Separate Next.js and FastAPI containers validated on Alibaba Cloud ECS System invariant: A generated clip cannot enter the timeline until it has been normalized, persisted, registered, and verified as a project output. Inspiration AI media has a handoff problem. Research tools can understand a source. Generation models can create an image or clip. Editors can assemble media. Publishing tools can prepare release copy. But when work moves between them, the context that made the asset useful is often lost. A report becomes notes with no path back to the source. A script becomes a collection of prompts. Generated clips arrive without stable IDs, continuity history, or edit state. The final package becomes a folder of files whose relationship to the original evidence exists only in chat history. Chinwag was built around those handoffs. The workspace carries evidence into writing, writing into media generation, verified media into editing, and the finished edit into publishing. Specialist agents narrow the decision at each stage; project files preserve what the next stage needs; deterministic checks decide whether an output is safe to use. The user experiences one production room, even though the work crosses models, tools, storage systems, and runtimes. What it does A user can begin with a report, an uploaded source, a web link, a draft, or a premise. The Newsroom reads and researches that material, then produces evidence-backed artifacts and drafts. Creator turns approved work into a script, storyboard, visual direction, and a bounded clip plan. Picasso creates still assets with qwen-image-2.0-pro . Video generates one wan2.7-t2v clip at a time and verifies the saved output before the sequence advances. Editor places only verified output IDs into the live timeline. Publisher prepares the titles, captions, descriptions, articles, metadata, and release material around the finished work. Each handoff becomes project state rather than another message in a transcript: Production stage What remains in the project Evidence Sources, extracted content, research artifacts, and source-grounded notes Direction Scripts, storyboards, shot lists, continuity anchors, and bounded clip plans Media Generated images and normalized, verified Wan video outputs Edit Stable clip IDs, ordered timeline state, trims, layers, and rendered MP4s Release Titles, captions, descriptions, articles, metadata, and publishing packages The result is not a loose download. It is a typed project output with a name, kind, storage path, prompt context, and stable ID that agents and editors can reopen without reconstructing the production history from chat. How we built it The architecture grew from one rule: a successful model call is only an intermediate state . Source material │ ▼ Evidence-aware research ──► script / storyboard / clip plan │ ▼ one Wan task per clip │ download → transcode → probe │ ▼ persist in OSS + Postgres │ verify the saved output │ ▼ append / replace timeline state │ ▼ validate → ffmpeg render → Outputs The application is split into a Next.js workspace and a FastAPI agent service. PostgreSQL stores users, projects, folders, files, and chat state. Alibaba Cloud OSS stores the heavier binary objects: uploaded sources, images, audio, generated clips, and rendered video. This follows the natural boundary of the data: relational state remains queryable while media remains object storage. Alibaba Cloud describes OSS as object storage for unstructured data including documents, images, audio, and video. The agent layer uses Qwen Agent Assistant , GroupChat , BaseTool , and explicit function_list capability sets. That is important: each worker can call only the tools needed for its job. Qwen Agent's own extension model defines custom tools through BaseTool and gives each assistant an explicit tool list. Chinwag uses that primitive to make agent roles enforceable in code rather than merely suggested in prompts. Each model has a specific job Chinwag does not send every task to one model. Model choice follows the shape of the work: qwen3.7-plus is the shared reasoning model for the Newsroom and Creator teams. It handles planning, source-grounded synthesis, multimodal source understanding, delegation, and tool use. qwen-image-2.0-pro is Picasso's default image model for thumbnails, key art, reference frames, and other still assets. wan2.7-t2v is the video model. Chinwag uses its 2–15 second generation range as a production boundary and builds longer sequences from verified clips. qwen-flash handles the small utility task of naming chats, where a full reasoning run would add cost without improving the result. The distinction is architectural rather than cosmetic. High-context reasoning stays with qwen3.7-plus ; specialized media work goes to the corresponding generation model; and a short, low-cost model handles a bounded utility request. Custom skills turn instructions into runtime policy In Chinwag, skills are project-scoped operating procedures. An agent reads the relevant skill through a restricted Qwen tool before it begins work, so the method travels with the project instead of depending on a growing system prompt or the agent's recollection of an earlier conversation. Three examples are provisioned with every project: nia-source-reader-skill.md defines typed source selection and evidence rules. Nia must use the text/PDF reader for textual material and the multimodal reader for images. If a read fails, it must stop rather than infer content from metadata. video-creator-skill.md constrains Video to one production-ready clip, then requires generate_video_asset followed by verify_video_output . One retry is allowed for the same clip; a second verification failure stops the sequence. editor-timeline-skill.md requires stable output IDs and a complete order before Editor can emit an append or replace timeline mutation. The skill readers themselves are capability-scoped. Video receives read_video_creator_skill but cannot browse unrelated project skills. Editor receives read_editor_timeline_skill . Nia receives read_source_reader_skill . The general drafting worker can use broader list_skills and read_skill tools when the assignment genuinely requires them. Worker Required skill Allowed production tools ────────── ───────────────────────────── ───────────────────────────────────── Nia source-reader method list/read source, write artifact Video video-creator method generate clip, verify saved output Editor editor-timeline method open timeline, place verified clips Publisher publication role contract read materials, write final package The distinction is useful in practice. A prompt can suggest how an agent should behave; the combination of a required skill reader and a narrow function_list determines what it can actually do. Chinwag's extension point is this custom Qwen tool and skill system. The implementation is visible in backend/tools/skills.py , the default skill definitions in src/lib/projectDefaults.ts , and the role-specific capability lists in backend/agents . Why the system uses multiple agents A source-reading task and a timeline mutation carry different kinds of risk. Source work must preserve evidence and stop when content cannot be read. Production work must preserve asset identity, ordering, provider constraints, and edit state. Putting both inside one universal agent would give a single context every instruction, every tool, and every intermediate result, even when most of them are irrelevant to the next decision. This is not only a token-budget concern: the original Lost in the Middle study found that language models can use long contexts unevenly depending on where relevant information appears. Chinwag therefore keeps durable knowledge in project artifacts and brings the relevant method, evidence, and tools into the active stage. Chinwag instead uses two Qwen GroupChat teams. The newsroom is led by Maya and includes Nia for source reading, Rafi for research, a drafting worker, and a time-aware worker. Creator mode is led by Creator, with Scriptwriter, Picasso, Video, Editor, and Publisher. Each worker receives the context and capabilities required for one stage, while durable artifacts carry knowledge between stages. One universal agent Chinwag's bounded teams ────────────────────────────── ────────────────────────────── all sources source evidence all research │ all production instructions Newsroom all generation tools │ research artifact / draft all timeline state ▼ all publishing tools Creator lead │ │ ▼ specialist handoffs one expanding context ┌───────┼────────┬────────┐ one expanding capability surface Script Image Video Edit/Publish This structure does three things at once. It reduces context competition, because a video worker does not need the full research tool history to generate one approved clip. It narrows authority, because Editor cannot generate media and Video cannot mutate the timeline. And it improves diagnosis, because every streamed action has a named worker, tool, and result rather than appearing as an opaque step inside one large run. Shared project context │ ├── evidence needed now ──► the active worker's context ├── method needed now ────► the worker's required skill └── actions allowed now ──► the worker's function_list The user still experiences one production room; the system avoids one unbounded agent. The agents are specialized by failure contract as much as by job title. Scriptwriter cannot generate video. Video cannot quietly edit a timeline. Editor cannot invent a missing clip. Nia cannot produce source-backed claims without successfully reading the source. The lead agent coordinates these boundaries and passes durable file IDs instead of relying on conversational memory alone. Chinwag also avoids treating multi-agent as automatic parallelism. The benefit here is specialization: the right worker receives the right capability surface. The video path remains sequential because clip 2 should not begin before clip 1 has been saved and verified. The architecture uses specialization where it improves context and control, and serialization where downstream correctness depends on an earlier result. For the user, this still feels like one room. The lead agent chooses the specialist, the interface streams the handoff, and each result returns to the same project. The complexity is inside the capability boundary rather than pushed onto the person making the work. The orchestration is implemented in backend/newsroom_group.py and backend/agents/creator/team.py . The token budget shapes the workflow The track asks teams to maximize output quality under a limited token budget .
